# Requirements Catalog

Source: [vision.md](vision.md). Terms are defined in [glossary.md](glossary.md).

The proxy is vendor-neutral and supports Chargers and Backends using the protocol in C-001. No vendor-specific integration is required.

## Functional Requirements

| ID     | Title                              | User Story                                                                                                                                                                                                                         | Priority | Status |
|--------|------------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|----------|--------|
| FR-001 | Connect Charger                    | As a Charger Owner, I want my Charger to connect to the proxy with one OCPP connection so that it can talk to several backends without knowing about them.                                                                         | High     | Open   |
| FR-002 | Allow Known Chargers Only          | As a Proxy Administrator, I want only Chargers on an allowlist to connect so that unknown devices cannot use the proxy.                                                                                                            | High     | Open   |
| FR-003 | Relay Charger Messages             | As a Backend Operator, I want the status, meter and statistics messages the Charger initiates sent to the Primary Backend and to every Secondary Backend configured for them so that every backend has current information.         | High     | Open   |
| FR-004 | Return Primary Replies to Charger  | As a Charger Owner, I want the Charger to receive the Primary Backend's replies for decisions, including Card Authorization, and only local acknowledgements for designated queued updates during an outage, so that charging behavior stays predictable. | High | Open |
| FR-005 | Relay Permitted Commands           | As a Backend Operator, I want the Commands my Command Policy permits relayed to the Charger so that I can control charging within my role.                                                                                          | High     | Open   |
| FR-006 | Route Replies to Originator        | As a Backend Operator, I want the Charger's reply to my Command returned to my backend only so that other backends never see or confuse my replies.                                                                                 | High     | Open   |
| FR-007 | Configure Allowed Commands         | As a Proxy Administrator, I want to configure per Backend which Commands are forwarded, answered by the proxy, or refused so that each Backend can only do what its role requires.                                                  | High     | Implemented   |
| FR-008 | Assign Exclusive Commands Once     | As a Proxy Administrator, I want the proxy to report an error and stop at startup when more than one Backend is configured to forward the same Exclusive Command so that Backends can never send conflicting Commands.               | High     | Implemented   |
| FR-009 | Answer Commands Locally            | As a Proxy Administrator, I want the proxy to answer refused-but-harmless Commands with a standard answer so that a Backend whose Command is not permitted continues to work without affecting the Charger.                        | Medium   | Open   |
| FR-010 | Deliver Billing Messages           | As a Secondary Backend Operator, I want transaction starts, stops and meter readings delivered to my backend so that I can handle billing, payments or statistics.                                                                 | High     | Open   |
| FR-011 | Store and Forward Billing          | As a Secondary Backend Operator, I want permitted Billing Messages retained until delivery and delivered in order after outages, without an attempt limit and with undelivered messages discarded only when the queue is full or their type is excluded by that backend's configured forwarding policy, so that delivery failures do not lose Transaction information. | High | Open |
| FR-012 | Map Transaction Numbers            | As a Backend Operator, I want transaction numbers translated between the Primary Backend and each Secondary Backend so that each backend sees consistent transactions.                                                             | High     | Open   |
| FR-013 | Configure Proxy                    | As a Proxy Administrator, I want to configure the proxy with a configuration file so that I can define Chargers, Backends and policies without changing code.                                                                       | High     | Implemented   |
| FR-014 | Reject Invalid Configuration       | As a Proxy Administrator, I want an invalid configuration to be refused at startup so that I find mistakes before Chargers connect.                                                                                                 | Medium   | Implemented   |
| FR-015 | Authenticate to Backends           | As a Proxy Administrator, I want to choose per Backend between no credentials, a password, or passing on the Charger's credentials so that the proxy fits each Backend's login.                                                    | High     | Implemented   |
| FR-016 | Authenticate Chargers              | As a Proxy Administrator, I want to optionally require a password from a Charger so that only the real device can connect.                                                                                                          | Medium   | Implemented   |
| FR-017 | Mask Logged Data                   | As a Proxy Administrator, I want credentials and message contents masked in logs so that sensitive data does not leak.                                                                                                              | Medium   | Open   |
| FR-018 | Configure Multiple Backends        | As a Proxy Administrator, I want to configure one Primary Backend and any number of named Secondary Backends so that one Charger can serve billing, energy management and statistics Backends at the same time.                    | High     | Open   |
| FR-019 | Reserve Authorization for Primary  | As a Primary Backend Operator, I want the proxy to refuse a configuration that lets a Secondary Backend forward an Authorization Command so that no Secondary Backend can start a charging session for a card I denied.            | High     | Implemented   |
| FR-020 | Pause and Resume Charging          | As a Secondary Backend Operator, I want to lower, pause and resume the charging power of a running Transaction with the Exclusive Command assigned to me so that I can follow solar surplus without ending the Transaction.        | High     | Open   |
| FR-021 | Store and Forward Primary Updates  | As a Backend Operator, I want `StatusNotification`, `MeterValues`, and `StopTransaction` messages retained and delivered in order after a Primary Backend outage, with an immediate local acknowledgement, so that updates are not lost when the service recovers. | High | Open |

## Non-Functional Requirements

| ID      | Title                    | Requirement                                                                                                                       | Category        | Priority | Status      |
|---------|--------------------------|-----------------------------------------------------------------------------------------------------------------------------------|-----------------|----------|-------------|
| NFR-001 | Charging Isolation       | An outage or rejection of any Secondary Backend must cause 0 delayed or failed replies to the Charger.                            | Availability    | High     | Open        |
| NFR-002 | Backend Answer Timeout   | The proxy must wait at most 30 seconds (default, configurable per backend) for a backend answer.                                  | Performance     | Medium   | Implemented        |
| NFR-003 | Reconnect Backoff        | Reconnection delays must start at 1 second, double up to 300 seconds, with ±50% randomization, per Backend.                         | Availability    | Medium   | Open        |
| NFR-004 | Durable Queue Size       | The proxy must hold at least 10,000 Billing Messages (default, configurable) per Secondary Backend across proxy restarts.          | Availability    | High     | Open        |
| NFR-005 | Billing Retention        | 0 undelivered Billing Messages may be discarded because of timeouts, backend rejections, retry counts, or missing transaction mappings; retries have no attempt limit. Queue overflow and exclusion by the backend's configured forwarding policy are the only discard exceptions. | Availability | High | Open |
| NFR-006 | Atomic State Writes      | State files must be written atomically; 0 corrupt files may result from a crash during a write.                                   | Availability    | High     | Open        |
| NFR-007 | Secrets Outside Config   | 0 passwords may be stored in the configuration file; they are read from environment variables.                                    | Security        | High     | Implemented        |
| NFR-008 | Test Suite               | The automated test suite must pass 100% and the linter (ruff, line length 120) must report 0 errors before a release.             | Maintainability | Medium   | Implemented |
| NFR-009 | Secondary Isolation      | An outage, slowness or rejection of one Secondary Backend must cause 0 delayed or lost messages to any other Secondary Backend.     | Availability    | High     | Open        |
| NFR-010 | Backend Count            | The proxy must serve at least 5 Secondary Backends per Charger session at the same time.                                           | Scalability     | Medium   | Open        |
| NFR-011 | Primary Outage Recovery   | After a session starts, a Primary Backend outage must not close the Charger connection. The proxy must retry indefinitely, retain up to 10,000 eligible updates per Charger across restarts, replay them in order, and log/drop the oldest only on overflow. | Availability | High | Open |

## Constraints

| ID    | Title                  | Constraint                                                                                                | Category    | Priority | Status      |
|-------|------------------------|-----------------------------------------------------------------------------------------------------------|-------------|----------|-------------|
| C-001 | Protocol               | The proxy must speak OCPP 1.6J (JSON over WebSocket) to the Charger and backends.                         | Technical   | High     | Open        |
| C-002 | Runtime Platform       | The proxy must run on Python 3.14 or newer.                                                               | Technical   | High     | Implemented |
| C-003 | Deployment             | The proxy must be deployable as a Docker image on a LAN-only host (TrueNAS SCALE).                        | Operational | High     | Implemented |
| C-004 | One Primary Backend    | Each Charger session must have exactly one Primary Backend and zero or more Secondary Backends.           | Technical   | High     | Open        |
